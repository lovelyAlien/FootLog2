<objective>
클라이언트가 백엔드로부터 발급받은 access/refresh 토큰을 OS 보안 저장소에 안전하게 보관하고,
만료 임박 시 사용자가 401을 겪기 전에 선제적으로 갱신하며(D-04), 이후 모든 서버 요청에
재사용하는 인증 클라이언트 모듈을 만든다.

Purpose: REQ-auth-session-token / ROADMAP 성공기준 2의 클라이언트측 전부 — "안전하게 저장하고,
만료 시 갱신하며, 이후 모든 서버 요청에 사용한다". 10-07의 검증 화면과 Phase 12의 동기화가
이 모듈 하나만 쓰면 되도록 만든다.
Output: `src/auth/` 아래 계약(config) / 런타임 의존성(deps) / 저장소(tokenStore) /
API 클라이언트(authApi) + 테스트 더블과 테스트.

**TDD 순서(.claude/skills/test-driven-development):** Task 1(계약+더블) → Task 2(테스트, RED) →
Task 3(구현, GREEN). 순서를 바꾸지 않는다.

**이 플랜은 UI를 만들지 않는다.** 카카오 SDK 호출과 화면은 10-07 소관이다. 여기서 만드는 것은
"토큰을 받아서 보관하고 갱신하고 붙여주는" 순수 로직뿐이며, `@react-native-seoul/kakao-login`을
import하지 않는다 — 그래야 이 모듈 전체가 네이티브 모듈 없이 Jest(node 환경)에서 테스트된다.

**이 저장소의 DI 규약을 따른다(`src/notifications/`).** 네이티브 패키지를 직접 import하는 파일은
`deps.ts` 하나뿐이고, 로직 파일들은 `config.ts`가 정의한 좁힌 타입 계약만 받는다. 테스트는
`testing/` 아래 손수 작성한 인메모리 더블을 주입한다. 목킹 프레임워크를 쓰지 않는다.
</objective>

`AuthError`는 `kind` 필드로 세 가지를 구분한다:
