**(1) `app.config.js` 신규 작성(저장소 루트).** `app.json`은 **한 글자도 수정하지 않는다.**
`module.exports = ({ config }) => ({ ...config, plugins: [...(config.plugins ?? []), ['@react-native-seoul/kakao-login', { kakaoAppKey: process.env.KAKAO_NATIVE_APP_KEY }]] })`
형태의 함수형 export를 쓴다.
`process.env.KAKAO_NATIVE_APP_KEY`가 비어 있으면 **명확한 한글 메시지와 함께 throw한다** —
"KAKAO_NATIVE_APP_KEY 환경변수가 없습니다. .env.example을 참고해 .env에 값을 넣으세요"처럼.
키 없이 조용히 빌드되면 런타임에 원인 파악이 어려운 카카오 SDK 초기화 실패로만 드러난다.
파일 상단 주석에 (a) `app.json`을 남겨두는 이유(`src/notifications/infoPlist.test.ts`의 정적
파싱 회귀 가드), (b) 이 파일이 `config` 인자로 app.json 내용을 받는다는 Expo 동작, (c) 여기서
`ios.infoPlist`의 권한 문구를 절대 덮어쓰지 않는다는 규약(Phase 2 Pitfall 5)을 남긴다.

**(3) `src/auth/kakaoLogin.ts`** — SDK 호출과 백엔드 교환을 잇는 얇은 오케스트레이션.
- `import { login as kakaoSdkLogin } from '@react-native-seoul/kakao-login';` — 이 저장소 DI
  규약대로 SDK를 직접 부르는 파일은 이 하나로 한정한다(`src/notifications/deps.ts`와 같은 역할).
  `src/auth/authApi.ts`/`tokenStore.ts`는 여전히 SDK를 모른다.
- `export async function signInWithKakao(deps = defaultAuthApiDeps): Promise<AuthTokens>`:
  1. `const kakaoToken = await kakaoSdkLogin();` — `login()`은 카카오톡 설치 시 앱 전환, 미설치 시
     웹 로그인 폴백을 SDK가 자동 처리한다(D-13의 채택 근거). `loginWithKakaoAccount()`는 항상
     계정 입력을 강제하므로 쓰지 않는다.
  2. SDK 호출이 throw하면(사용자 취소 포함) `AuthError`의 `'rejected'`로 감싸 던진다. 취소와 실패를
     구분할 수 있는 에러 코드가 SDK에서 확인되면 구분해도 되지만, **확인되지 않은 코드 문자열을
     추측으로 분기하지 않는다** — 확인 못 하면 하나로 합치고 그 사실을 주석에 남긴다.

     우리 시스템에 남지 않는다).
