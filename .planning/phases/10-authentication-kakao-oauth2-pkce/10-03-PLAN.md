**두 개의 JwtDecoder가 필요한 이유(중요):** 10-RESEARCH.md Pattern 4의 디코더는 커스텀
`OAuth2TokenValidator`로 `token_use = "access"`를 강제한다. 그런데 10-05의
`POST /api/auth/refresh`는 refresh 토큰을 검증해야 하므로 같은 디코더를 재사용할 수 없다.
따라서 access 전용 디코더에 `@Primary`를 붙여 `oauth2ResourceServer`가 그걸 자동 주입받게 하고,
refresh 전용 디코더는 별도 빈 이름으로 둔다. `@Primary`가 없으면 `JwtDecoder` 타입 빈이 2개라
필터 체인 자동설정이 모호성 오류로 기동 실패한다.

**`/actuator/**`를 permitAll로 두는 이유(중요):** Phase 9의 `HealthCheckSmokeTest` Test 2/3과
`StagingProfileBootTest` Test 3은 `/actuator/env`·`/actuator/beans`가 **404**임을 단언한다 —
`management.endpoints.web.exposure.include: health`가 그 외 엔드포인트를 아예 매핑하지 않기
때문이며, 이것이 T-9-02(정보 노출) 회귀 게이트다. `/actuator/**`를 authenticated로 두면 그
단언들이 401로 바뀌어 게이트의 의미가 사라진다(노출 목록이 실수로 넓어져도 401만 보고 넘어가게 됨).
permitAll로 두면 "노출 목록이 유일한 제어"라는 원래 계약이 그대로 유지된다.

**(1) `backend/build.gradle.kts`.** `dependencies` 블록에 아래 5개 좌표를 기존 정렬 관례에 맞춰
추가한다. Boot BOM이 버전을 관리하므로 명시적 버전을 절대 붙이지 않는다.
- `implementation("org.springframework.boot:spring-boot-starter-security")`
- `implementation("org.springframework.boot:spring-boot-starter-security-oauth2-resource-server")`
- `implementation("org.springframework.boot:spring-boot-starter-restclient")`
- `testImplementation("org.springframework.boot:spring-boot-starter-security-test")`
- `testImplementation("org.springframework.boot:spring-boot-starter-security-oauth2-resource-server-test")`

세 개의 `implementation`에 저장소 관례대로 `//` 주석을 남긴다:
- resource-server 스타터: 이 스타터 하나가 `spring-security-oauth2-jose`와
  `com.nimbusds:nimbus-jose-jwt`를 전이적으로 가져와 `NimbusJwtEncoder`/`NimbusJwtDecoder`로
  **자체** JWT를 발급·검증할 수 있게 한다(외부 IdP 토큰만 검증하는 용도가 아니다). 그래서
  `io.jsonwebtoken:jjwt`가 필요 없다.
- **Boot 4 아티팩트명 주의:** `spring-boot-starter-oauth2-resource-server`가 아니라
  `spring-boot-starter-security-oauth2-resource-server`다(Boot 3과 다름, 09의
  `spring-boot-starter-flyway` 명명 변경과 같은 계열).
- restclient 스타터: `RestClient.Builder` 자동설정을 main 스코프에 제공한다. Boot 4.1부터 REST
  클라이언트 지원이 별도 모듈로 분리됐다(Pitfall 5) — 42줄 부근의 `-restclient-test`는 테스트
  스코프 전용이라 이걸 대신하지 못한다.

`spring-boot-starter-restclient-test`는 **이미 존재하므로 다시 추가하지 않는다.**
좌표가 해석되지 않으면 추측으로 바꾸지 말고 `./gradlew dependencies` 출력과 대조한다.

**(2) `application.yml`(공통).** 최하단에 `jwt` 블록을 추가한다. 기존 `spring`/`management`
블록은 손대지 않는다.
- `jwt.issuer: footlog-backend`
- `jwt.access-token-ttl: PT30M` (D-03의 "15분~1시간" 범위 안에서 30분 선택 — ISO-8601 Duration)
- `jwt.refresh-token-ttl: P30D` (D-03)
- `jwt.secret: ${JWT_SECRET:local-and-test-only-insecure-placeholder-do-not-use-in-production}`

`jwt.secret` 위에 한글 주석으로 다음 세 가지를 반드시 남긴다:
(a) 이 기본값은 **로컬 개발과 테스트 전용**이며 비밀값이 아니다 — 어떤 실제 토큰도 이 키로
    서명되어서는 안 된다. (b) 기본값을 공통 프로파일에 둔 이유: 이 저장소의 통합 테스트들은
    활성 프로파일 없이(`@SpringBootTest` 단독) 돌기 때문에 로컬 프로파일에만 기본값을 두면
    테스트 컨텍스트가 기동되지 않는다(10-RESEARCH.md Open Questions #3의 절충안을 이 제약에 맞춰
    조정한 것). (c) staging은 `application-staging.yml`이 이 값을 **기본값 없는**
    `${JWT_SECRET}`으로 덮어쓰므로, 환경변수가 없으면 기동 자체가 실패한다 —
    즉 이 플레이스홀더가 배포 환경으로 새어 나갈 경로가 없다(D-11 계승).
기본값 문자열은 32바이트(=32 ASCII 문자) 이상이어야 한다. HS256은 최소 256비트 키를 요구하고
짧으면 Nimbus가 기동 시점에 예외를 던진다(Pitfall 2).

**`application-local.yml`은 수정하지 않는다** — 공통 프로파일의 기본값이 로컬에도 그대로
상속되므로 중복 선언이 필요 없다.

**(3) `application-staging.yml`.** 기존 `spring.datasource` 블록 아래에 최상위 `jwt` 블록을

`JWT_SECRET`이 미주입되면 기동이 즉시 실패하는 것이 **의도된 동작**임을 주석으로 남긴다
(`openssl rand -base64 32`로 생성, 10-01의 `.env.example` 참고).

**(4) `backend/src/main/kotlin/com/footlog/backend/config/JwtConfig.kt` 신규 작성.**
10-RESEARCH.md Pattern 4를 그대로 따르되, 디코더를 **두 개** 정의한다.
- `@ConfigurationProperties("jwt")` 또는 `@Value` 주입으로 `issuer`/`secret`/`accessTokenTtl`/
  `refreshTokenTtl`을 읽는 `JwtProperties`를 이 파일 또는 같은 config 패키지에 둔다. TTL은
  `java.time.Duration` 타입으로 받아 ISO-8601 문자열이 자동 변환되게 한다.
- `secretKey`는 `SecretKeySpec(secret.toByteArray(), "HmacSHA256")`.
- `@Bean fun jwtEncoder(): JwtEncoder` — `OctetSequenceKey.Builder(secretKey).algorithm(JWSAlgorithm.HS256).build()`를
  `ImmutableJWKSet(JWKSet(jwk))`로 감싸 `NimbusJwtEncoder`에 넘긴다.
- `@Bean @Primary fun jwtDecoder(): JwtDecoder` — `NimbusJwtDecoder.withSecretKey(secretKey).macAlgorithm(MacAlgorithm.HS256).build()`에
  `DelegatingOAuth2TokenValidator(JwtValidators.createDefault(), <token_use == "access" 검증기>)`를
  `setJwtValidator`로 설정.
- `@Bean fun refreshTokenDecoder(): JwtDecoder` — 같은 형태이되 검증기가 `token_use == "refresh"`를 요구.
- 두 검증기의 중복을 줄이기 위해 `private fun tokenUseValidator(expected: String): OAuth2TokenValidator<Jwt>`
  같은 헬퍼를 둔다. 실패 시 `OAuth2TokenValidatorResult.failure(OAuth2Error("invalid_token", ...))`를 반환한다.
- `@Primary`가 왜 필요한지(= `JwtDecoder` 빈 2개 → `oauth2ResourceServer` 자동 주입 모호성)와,
  `token_use` 구분 클레임이 없으면 탈취된 refresh 토큰으로 보호된 API를 직접 호출할 수 있게
  된다는 점을 한글 주석으로 남긴다.

**(5) `backend/src/main/kotlin/com/footlog/backend/config/SecurityConfig.kt` 신규 작성.**
10-RESEARCH.md Pattern 5를 따른다. `@Configuration @EnableWebSecurity`, `@Bean fun securityFilterChain(http: HttpSecurity): SecurityFilterChain`.
- `.csrf { it.disable() }` — stateless JWT API이고 쿠키 기반 세션이 없어 CSRF 벡터가 존재하지
  않는다는 근거를 주석으로 남긴다(10-RESEARCH.md Security Domain V3).
- `.sessionManagement { it.sessionCreationPolicy(SessionCreationPolicy.STATELESS) }`
- `.authorizeHttpRequests { it.requestMatchers("/actuator/**", "/api/auth/**").permitAll().anyRequest().authenticated() }`
- `.oauth2ResourceServer { it.jwt(Customizer.withDefaults()) }`
- `/actuator/**`를 permitAll로 두는 이유(위 `<context>`의 설명 — actuator 노출 잠금이 유일한
  제어여야 404 회귀 게이트가 유지된다)를 반드시 주석으로 남긴다. 그렇지 않으면 다음 사람이
  "보안상 조여야 한다"며 authenticated로 바꿔 Phase 9의 T-9-02 게이트를 무력화한다.
- `.and()` 체이닝을 쓰지 않는다(Pitfall 1).
