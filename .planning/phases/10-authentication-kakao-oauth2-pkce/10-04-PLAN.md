## ⚠️ D-14는 수정됐다 — 10-RESEARCH.md의 Pattern 1을 절대 구현하지 말 것

10-RESEARCH.md 본문 상단의 **⚠️ AMENDMENT 블록**과 10-PATTERNS.md 최상단의 **CRITICAL** 절이
정본이다. 요약하면:
- 백엔드는 `kauth.kakao.com/oauth/token`을 **호출하지 않는다.** 인가 코드 ↔ 토큰 교환 단계가
  이 phase의 백엔드 코드 경로에서 완전히 사라졌다 — 네이티브 SDK가 이미 그걸 내부에서 끝내고
  카카오 액세스 토큰을 JS 레이어에 직접 반환하기 때문이다.
- 따라서 `KakaoTokenClient` / `KakaoTokenResponse`를 만들지 않는다. `client_secret`,
  `code_verifier`(PKCE), `redirect_uri`는 이 플랜의 어떤 코드에도 등장하지 않는다.
- 10-RESEARCH.md의 **Pitfall 4**(`client_secret`이 항상 필요)는 카카오 API에 대한 사실로서는
  맞지만 **이번 구현에는 적용되지 않는다**(그 API를 아예 호출하지 않으므로). 감사 기록일 뿐이니
  실행 태스크에 반영하지 않는다.
- 여전히 유효해서 그대로 쓰는 것: **Pattern 2**(사용자정보 조회 + DTO), Pattern 3(V4, 10-02에서

- `@Component class KakaoUserInfoRestClient(restClientBuilder: RestClient.Builder) : KakaoUserInfoClient`
  — 생성자에서 `restClientBuilder.build()`로 `RestClient`를 만들어 필드에 보관한다.
  `RestClient.create()`로 직접 만들지 않는다(Boot의 자동설정 커스터마이저를 우회하게 되고,
  `MockRestServiceServer` 바인딩도 불가능해진다 — Pitfall 5).
- `fetchUserInfo` 구현은 10-RESEARCH.md Pattern 2 그대로: `restClient.get()`,
  `.uri("https://kapi.kakao.com/v2/user/me")`, `.header(HttpHeaders.AUTHORIZATION, "Bearer $kakaoAccessToken")`,
  `.retrieve().body(KakaoUserInfoResponse::class.java)`. 응답 본문이 null이면

`backend/src/main/kotlin/com/footlog/backend/auth/KakaoAuthService.kt`의 골격을 실제 구현으로 채운다.

`@Service class KakaoAuthService(private val kakaoUserInfoClient: KakaoUserInfoClient,
private val userRepository: UserRepository, private val jwtIssuerService: JwtIssuerService)`.

`@Transactional fun loginWithKakao(kakaoAccessToken: String): TokenResponse`의 흐름:
1. `val info = kakaoUserInfoClient.fetchUserInfo(kakaoAccessToken)` — 예외는 잡지 않고 그대로
   전파한다(10-05가 401로 매핑). **이 지점 이후 `kakaoAccessToken` 변수를 다시 쓰지 않는다.**
   저장하지도, 로그로 남기지도, 다른 객체에 넘기지도 않는다(D-14).
2. `val profile = info.kakaoAccount?.profile` — 두 단계 모두 안전 호출이다(D-07).
3. `val existing = userRepository.findByKakaoId(info.id)`
4. 있으면: `existing.nickname = profile?.nickname`, `existing.profileImageUrl = profile?.profileImageUrl`로
   **덮어쓴다**(D-06 — 카카오 최신값이 진실의 원천이다. 기존 값이 있고 새 값이 null일 때
   기존 값을 유지하지 않는다. 사용자가 카카오에서 프로필을 지운 상태를 그대로 반영하는 것이 D-06의 취지다).
   `@Transactional` 안이므로 dirty checking으로 반영되지만, 의도를 드러내기 위해
   `userRepository.save(existing)`를 명시적으로 호출한다.
5. 없으면: `User(id = UUID.randomUUID(), createdAt = OffsetDateTime.now(), kakaoId = info.id,
   nickname = profile?.nickname, profileImageUrl = profile?.profileImageUrl)`를 만들어 저장한다.
   **`info.id`를 `User.id`에 넣지 않는다** — `users.id`는 서버 소유 UUID이고 `kakao_id`는 별도
   외부 식별자다. 이 구분을 주석으로 명시한다.
6. `TokenResponse(accessToken = jwtIssuerService.issueAccessToken(user.id),
   refreshToken = jwtIssuerService.issueRefreshToken(user.id),
   expiresIn = jwtIssuerService.accessTokenTtlSeconds)`를 반환한다.

`@Transactional`을 메서드에 붙여, 카카오 조회 후 사용자 생성이 실패하면 부분 상태가 남지 않게 한다.

파일 상단 주석에 남길 것:
- D-14 수정 반영: 이 서비스는 카카오 토큰 **교환**을 하지 않는다. 클라이언트가 이미 받은
  액세스 토큰을 사용자정보 조회 1회에만 쓰고 폐기한다. `kauth.kakao.com/oauth/token`을 호출하는
  코드를 나중에 여기 추가하지 말 것 — 필요해지면 D-14를 다시 논의해야 한다.
- 동시성: 같은 카카오 계정으로 두 요청이 동시에 들어오면 5단계에서 둘 다 "없음"으로 판단해
  두 번 insert를 시도할 수 있다. 그때 `uq_users_kakao_id`(10-02)가 두 번째를 거부하므로 중복
  계정은 생기지 않는다(D-08). 1인 프로젝트 규모에서 그 경합의 재시도 처리는 하지 않고, 두 번째
  요청은 예외로 실패하는 것을 허용한다 — 사용자가 다시 로그인하면 성공한다.
