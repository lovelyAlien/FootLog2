    - `commitCheckin(db: MigratableDb, params: NewCheckinParams): Promise<SaveResult>` — 먼저 `isValidCoordinate({ lat, lng })`로 가드하고 실패 시 DB를 건드리지 않고 `{ ok: false, reason: 'invalid_coordinate' }` 반환. 그다음 `runWithSingleRetry`로 아래 시퀀스를 감싼다: `execAsync('BEGIN')` → `runAsync('INSERT INTO checkins (id, timestamp_utc, local_date_key, timezone_at_capture, lat, lng, accuracy_meters, location_source, created_at, updated_at, schema_version) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)', ...)` → `runAsync('DELETE FROM drafts WHERE id = ?', DRAFT_ROW_ID)` → `execAsync('COMMIT')`. 시퀀스가 throw하면 `execAsync('ROLLBACK')`을 시도하고(ROLLBACK 자체의 실패는 흡수) 재시도로 넘어간다. `note`/`photo_path`는 insert 시점에 넣지 않는다 — 저장 성공 이후 화면에서 `updateCheckinNoteAndPhoto`로 채운다(03-UI-SPEC.md SAVED 상태 계약). `schema_version`에는 `1`을 바인딩한다.

      DELETE가 반드시 INSERT **뒤에** 오고 같은 트랜잭션 안에 있어야 한다 — 순서를 뒤집으면 D-05가 요구하는 "insert 실패/재시도 중 강제종료 시 드래프트로 복구" 보장이 깨진다(Pitfall 5).
    - `getLatestCheckinCoordinate(db: MigratableDb): Promise<{ lat: number; lng: number } | null>` — `SELECT lat, lng FROM checkins ORDER BY created_at DESC LIMIT 1`
    - `updateCheckinNoteAndPhoto(db, id: string, args: { note: string | null; photoPath: string | null; now: string }): Promise<void>` — `UPDATE checkins SET note = ?, photo_path = ?, updated_at = ? WHERE id = ?`

    `src/checkin/checkinRepo.test.ts`(`@jest-environment node`)로 위 behavior 8개를 검증한다. 성공 경로와 좌표 가드, 최근 좌표 조회, 메모/사진 갱신은 `createTestDb()` + `migrateDbIfNeeded`의 실제 SQLite 엔진으로 검증한다. 실패/재시도 경로는 실제 엔진으로 디스크 실패를 재현할 수 없으므로 `MigratableDb`를 구조적으로 만족하는 인라인 fake db를 이 테스트 파일 안에 만들어(호출 카운터를 세고 N번째 `runAsync`까지 throw) 검증한다 — 03-PATTERNS.md가 지정한 예외 케이스다.
