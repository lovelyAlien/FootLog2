도메인별 패키지 3개에 엔티티와 리포지토리를 만든다.

`user/User.kt`: `@Entity @Table(name = "users")`, `@Id val id: UUID`,
`@Column(name = "created_at", nullable = false, updatable = false) val createdAt: OffsetDateTime`.
`users.id`는 DB 기본값 `gen_random_uuid()`가 있는 유일한 테이블이지만, 이번 phase에서 서버가
새 사용자를 만들지 않으므로 `@GeneratedValue`는 붙이지 않고 호출부 지정 UUID를 그대로 쓴다.

`checkin/Checkin.kt`: 09-RESEARCH.md Pattern 1의 엔티티를 그대로 작성한다 —
`@ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "user_id", nullable = false) val user: User`,
그리고 timestampUtc/localDateKey/timezoneAtCapture/lat/lng/accuracyMeters/locationSource/
note/photoPath/createdAt/updatedAt/schemaVersion을 `@Column(name = "snake_case")`로 매핑한다.
불변 필드(id, createdAt, user)는 `val`, 이후 변경되는 필드는 `var`로 둔다.
**`@GeneratedValue`를 절대 붙이지 않는다** — 클라이언트가 `crypto.randomUUID()`로 ID를 소유하고,
서버가 재발급하면 Phase 12 동기화 정합성이 깨진다(Pitfall 5). 이 이유를 코드 주석으로 남긴다.

`dailyreflection/DailyReflection.kt`: 같은 패턴으로 id(UUID, `@GeneratedValue` 없음), user(FK),
`date: LocalDate`, newPlaceAnswer/freeReflection(nullable), createdAt/updatedAt을 매핑한다.
`date`는 Postgres `DATE` 컬럼이므로 `OffsetDateTime`이 아니라 `java.time.LocalDate`를 쓴다.

리포지토리 3종은 각각 `interface XRepository : JpaRepository<X, UUID>` 한 줄이면 충분하다 —
이번 phase에는 커스텀 쿼리 메서드를 만들지 않는다(조회 API는 Phase 12 스코프).

작성 후 테스트를 실행해 GREEN을 확인한다. `ddl-auto=validate` 상태에서 컨텍스트가 뜬다는 것
자체가 "엔티티와 실제 스키마가 일치한다"는 증거다 — 불일치가 있으면 기동 단계에서 실패한다.
스키마 쪽이 틀렸다고 판단되면 V1~V3를 수정하지 말고(적용된 마이그레이션 불변 규율) 원인을
먼저 확인한 뒤 필요하면 새 `V4__*.sql`을 추가하는 방향으로 처리한다.
