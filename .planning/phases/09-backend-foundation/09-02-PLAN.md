**마이그레이션 규율(09-PATTERNS.md `## Shared Patterns`):** 한 번 적용된 `V*__*.sql` 파일은
사후 수정하지 않는다 — 스키마 변경은 항상 새 `V{n+1}__*.sql` 파일을 추가하는 방식이다.

`backend/src/main/resources/db/migration/`에 세 파일을 09-RESEARCH.md Pattern 2의 SQL 그대로
작성한다. 파일명은 Flyway 규약대로 `V1__create_users_table.sql`,
`V2__create_checkins_table.sql`, `V3__create_daily_reflections_table.sql`(더블 언더스코어).

V1: `users(id UUID PRIMARY KEY DEFAULT gen_random_uuid(), created_at TIMESTAMPTZ NOT NULL DEFAULT now())`
와 플레이스홀더 로우 `INSERT INTO users (id) VALUES ('00000000-0000-0000-0000-000000000001')`(D-02).
`gen_random_uuid()`는 Postgres 13+ core 내장이라 pgcrypto 확장이 필요 없다.

V2: `checkins` — 컬럼과 타입은 `id UUID PRIMARY KEY`(**DEFAULT 없음**),
`user_id UUID NOT NULL REFERENCES users(id)`, `timestamp_utc TIMESTAMPTZ NOT NULL`,
`local_date_key VARCHAR(10) NOT NULL`, `timezone_at_capture VARCHAR(64) NOT NULL`,
`lat DOUBLE PRECISION NOT NULL`, `lng DOUBLE PRECISION NOT NULL`,
`accuracy_meters DOUBLE PRECISION`, `location_source VARCHAR(32) NOT NULL`, `note TEXT`,
`photo_path TEXT`, `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`,
`updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `schema_version INTEGER NOT NULL DEFAULT 1`.
인덱스 `idx_checkins_local_date_key(local_date_key)`와 `idx_checkins_user_id(user_id)`를 만든다.

V3: `daily_reflections` — `id UUID PRIMARY KEY`(**DEFAULT 없음**),
`user_id UUID NOT NULL REFERENCES users(id)`, `date DATE NOT NULL`, `new_place_answer TEXT`,
`free_reflection TEXT`, `created_at TIMESTAMPTZ NOT NULL DEFAULT now()`,
`updated_at TIMESTAMPTZ NOT NULL DEFAULT now()`, `UNIQUE (user_id, date)`.
클라이언트는 `UNIQUE(date)`지만 서버는 다중 사용자를 전제하므로 `(user_id, date)`로 넓히는 것이
의도된 divergence다(09-RESEARCH.md A4) — 클라이언트와 맞추겠다고 되돌리지 않는다.

각 파일 상단에 한글 주석으로 (a) 대응하는 클라이언트 DDL 위치(`src/db/schema.ts`), (b) 이
파일은 적용 후 절대 수정하지 않고 변경 시 새 `V4__*.sql`을 추가한다는 규율, (c) V2/V3의
`id`에 기본값 생성기를 붙이면 안 되는 이유(클라이언트가 `crypto.randomUUID()`로 ID를 소유,
Phase 12 동기화 전제)를 남긴다.

`schema_version` 컬럼은 클라이언트 스키마 버전을 담는 메타데이터일 뿐 Flyway의
`flyway_schema_history`와 무관하다는 점도 V2 주석에 명시한다(09-RESEARCH.md A3/Open Question 2 —
실제 채우기 로직은 Phase 12 스코프).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Flyway 마이그레이션 SQL → PostgreSQL | 스키마를 변경하는 유일한 경로. 정적 파일이며 런타임 사용자 입력이 개입하지 않는다 |
| 클라이언트가 발급한 UUID → 서버 레코드 식별자 | Phase 12에서 신뢰 경계가 되는 지점(이번 phase에는 이 경로를 여는 API가 없다) |

이번 플랜에는 인증(V2)/세션(V3)/접근제어(V4) 표면이 없다 — 도메인 API 엔드포인트를 만들지
않기 때문이다. V5(입력 검증)는 마이그레이션 SQL이 정적 파일이라 적용 지점이 없다.
