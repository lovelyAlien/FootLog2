# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Scope Boundary (read first)

Phase 5의 UI 표면은 오늘 뷰(Phase 4) 바텀시트 리스트의 완료된 행을 탭하면 열리는 **체크인 상세화면** 하나와, 그 리스트 행 자체의 **스와이프 삭제** 인터랙션에 한정된다. 아래가 이 phase의 전체 UI 범위다:

1. **체크인 상세화면(신규 라우트, push, 탭바 노출 유지)** — 시간(모노스페이스) → 정적 지도 미리보기 → "지도 앱에서 열기" → 사진 → 메모, 고정 순서(REQ-checkin-detail-layout).
2. **메모 인라인 편집 + 저장되지 않은 변경 이탈 경고** — 자동저장 아님(D-01, REQ-checkin-detail-base).
3. **`AppState` 백그라운드 강제 flush** — 인앱 이탈 경고와는 다른 별도 경로(D-02, REQ-checkin-detail-flush).
4. **"지도 앱에서 열기" 딥링크 버튼** — muted 톤 텍스트 버튼(REQ-maps-deeplink).
5. **사진 교체/삭제** — 기존 액션시트 재사용 + 확인 없는 즉시 삭제(D-03, D-04).
6. **수정 저장 실패 UI** — 최초 저장 실패(`CheckinActionCard` SAVE_FAILED)와 동일 패턴 재사용.
7. **바텀시트 리스트 행 스와이프 삭제 + 4초 undo 스낵바** — 올리브그린 어포던스, 빨강 금지(REQ-checkin-swipe-delete).
8. **`CheckinListRow`를 탭 가능하게 전환** — Phase 4에서 의도적으로 비활성화(D-03, 04-CONTEXT.md)했던 것을 이 phase가 뒤집는다.

**이 phase가 만들지 않는 것 (05-CONTEXT.md 근거):**
- 상세화면 안의 체크인 전체 삭제 버튼 — D-05, 삭제는 리스트 스와이프로만. 상세화면은 편집 전용 공간으로 유지.
- 사진/체크인 전체 삭제에 대한 4초 undo — 체크인 전체 삭제(REQ-checkin-swipe-delete)에만 undo가 있고, 사진 단일 필드 삭제(D-04)는 undo 없음. 둘을 혼동해 같은 컴포넌트로 묶지 않는다.
- 과거 날짜 뷰(Phase 6)에서 상세화면으로 들어오는 배선 — 진입점은 오늘 뷰 리스트 행 하나뿐, Phase 6이 자신의 배선을 추가할 때 이 상세화면을 재사용은 하되 이 UI-SPEC이 그 통합을 정의하지 않는다.
- 회고(Phase 7)의 5초 디바운스 자동저장 패턴 — 참고만 하고 채택하지 않음(D-01).

## Spacing Scale

Declared values (Phase 1 `src/theme/tokens.ts`에서 그대로 가져옴 — 새로 발명하지 않음):

| Token | Value | Usage (이 phase) |
|-------|-------|-------|
| 2xs | 4px | 사진 삭제 아이콘 배지 내부 여백 |
| xs | 8px | 사진 삭제 아이콘 배지의 사진 모서리 기준 inset |
| sm | 12px | 상세화면 섹션 내부 상하 여백(지도 미리보기↔"지도 앱에서 열기" 버튼 사이 등) |
| md | 16px | 스와이프 삭제 어포던스 좌우 내부 패딩, 스낵바 내부 좌우 패딩 |
| lg | 24px | 상세화면 좌우 콘텐츠 패딩(전 섹션 공통), 섹션 간 세로 간격 |
| xl | 32px | 사용 안 함 이 phase에서는 |
| 2xl | 48px | 사용 안 함 이 phase에서는 |
| 3xl | 64px | 사용 안 함 이 phase에서는 |

> **`sm=12px`에 대한 노트(체커의 표준 8-point 세트 {4,8,16,24,32,48,64} 예외 플래그 대응):** `sm=12px`는 이 phase가 새로 만든 값이 아니라 Phase 1에서 확정돼 `src/theme/tokens.ts`에 이미 존재하는 프로젝트 고유 spacing 스케일의 일부이며, Phase 2~4에서도 동일하게 재사용돼 왔다. 이 phase는 그 값을 그대로 참조할 뿐 스케일 자체를 바꾸지 않는다 — 값 변경은 phase-local UI-SPEC의 권한 밖이며, 필요하다면 프로젝트 전역 `tokens.ts`/DESIGN.md 개정과 사용자 승인이 선행돼야 한다.

Exceptions:
- **44×44pt 최소 터치 타겟** — "지도 앱에서 열기" 텍스트 버튼, 사진 삭제 아이콘 배지(`hitSlop`으로 확장, 시각적으로는 더 작아도 됨), 스낵바의 "실행취소" 액션, 상세화면 헤더 뒤로가기 버튼(iOS 시스템 기본).
- **정적 지도 미리보기 고정 높이:** 160px(spacing 스케일의 배수는 아니지만 `photoBox`류 기존 컴포넌트 크기 결정과 동일한 근거의 컴포넌트 치수 — spacing 토큰 자체가 아님). 전체 너비 사용, `radius.md`(8px) 모서리.
- **빈 사진 슬롯 높이:** 160px, 정적 지도 미리보기와 시각적 리듬 일치(둘 다 화면 너비를 쓰는 사각형 블록).
- **스와이프 삭제 어포던스 폭:** 72px(리스트 행과 동일한 44px 높이), `colors.accent` 배경.

## Typography

`src/theme/tokens.ts`의 네임드 시맨틱 토큰만 사용 — 새 크기/굵기 추가 없음.

> **3-weight 시스템(400/500/600)에 대한 노트(체커의 max-2-weights 규칙 대응):** 이 phase의 Typography 테이블에는 400(`helperText`, `journalEntry`), 500(`timestamp`, `placeName`), 600(`screenTitle`) 세 가지 굵기가 등장하지만, 이 세 굵기는 Phase 5가 새로 도입한 것이 아니다. FootLog는 DESIGN.md에서 **SF Pro 시스템 폰트 / SF Mono 모노스페이스 / Newsreader 이탤릭 세리프**의 3계층 타이포그래피 체계를 프로젝트 전역 결정으로 이미 확정했고(`REQ-design-tokens`, Phase 1에서 `src/theme/tokens.ts`로 export), Phase 2~4가 그 체계를 변경 없이 그대로 재사용해왔다. Phase 5는 이 테이블에서 **새 사이즈나 새 굵기를 단 하나도 추가하지 않는다** — `timestamp`/`placeName`/`helperText`/`journalEntry`/`screenTitle` 모두 이전 phase에서 이미 확립·사용 중이던 토큰을 그대로 재참조할 뿐이다. 체커가 제안한 첫 번째 수정안(예: `screenTitle`을 500으로 낮춰 2-weight로 맞추는 것)을 따르면 이 phase가 DESIGN.md의 이미 승인된 타이포그래피 체계에서 사용자 승인 없이 이탈하게 되는데, 이는 프로젝트 CLAUDE.md의 "DESIGN.md에 정의된 폰트/색상/여백/미학 방향에서 명시적 사용자 승인 없이 벗어나지 않는다"는 규칙을 정면으로 위반한다. 따라서 이 값들은 phase-local 결정이 아니라 **프로젝트 전역 DESIGN.md 개정 + 명시적 사용자 승인**이 있어야만 바뀔 수 있는 범위이며, 이번 revision에서는 어떤 토큰/굵기/크기도 변경하지 않는다.

| Role | Token (tokens.ts) | Size | Weight | Line Height | 이 phase에서 쓰이는 곳 |

**금지 사항:** `typography.journalEntry`는 메모 편집 텍스트필드 하나에만 — 버튼 라벨/헤더/안내 문구에는 절대 쓰지 않는다(Phase 3/4 원칙 계승).

## Color

DESIGN.md/`tokens.ts`의 기존 팔레트를 그대로 사용 — **이 phase가 새 색상 토큰을 발명하지 않는다.** 다만 기존 `colors.accent`를 승인된 6개 용도 밖의 새 맥락(스와이프 삭제)에 재사용하는 확장 결정이 하나 있다(아래 참고).

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#F4F1EA` (`colors.background`) | 상세화면 배경 |
| Secondary (30%) | `#FBFAF6` (`colors.surface`) | 메모 텍스트필드 배경, 사진 슬롯 배경(사진 있을 때는 사진 자체) |
| Accent (10%) | `#7C8660` (`colors.accent`) | 이 phase의 신규 사용처는 **스와이프 삭제 어포던스 배경** 1곳뿐(아래 "색상 결정" 참고) — 체크인 버튼 등 기존 6개 승인 용도는 이 phase에서 다시 그리지 않음 |
| Pin soft | `#DDC0AC` (`colors.pinSoft`) | 정적 지도 미리보기의 단일 마커(이미 저장된 체크인이므로 Today 뷰의 "저장된 핀"과 동일 규칙 적용 — `colors.pin`이 아니라 `pinSoft`) |
| Destructive(체크인 전체 삭제 스와이프) | `colors.accent` (신규 색상 아님, 재사용) | 스와이프 삭제 어포던스 배경 + 아이콘은 `colors.surface` |
| Destructive(사진 삭제) | `colors.textMuted` | 삭제 아이콘 배지, semantic red 아님 — "가벼운 편집 액션"(D-04) 취급에 맞춰 accent도 별도 destructive 색도 쓰지 않음 |

Accent 예산 확인: 이 phase가 accent를 쓰는 유일한 신규 위치는 스와이프 삭제 배경이며, "액센트 1개, 절대 늘리지 않음" 원칙은 **새 색상을 만들지 않았으므로** 유지된다(기존 색의 새 용도 확장, Phase 4가 궤적선에 `accentSoft`를 재사용한 것과 동일한 선례).

### 색상 결정: 스와이프 삭제 어포던스는 `accent`(빨강 아님)를 재사용

REQUIREMENTS.md(REQ-checkin-swipe-delete)와 `footlog-product-design.md` T11이 모두 "빨간색이 아니라 기존 올리브그린 톤 유지"라고 명시한다 — "기존"이라는 표현이 핵심: 팔레트에 올리브그린은 `colors.accent` 하나뿐이므로, 이는 새 색상을 만들라는 지시가 아니라 **이미 있는 accent를 재사용하라는 지시**로 읽는 게 문서와 가장 일치한다. DESIGN.md의 "시맨틱 색상 없음"(success/warning/error 색 자체를 두지 않음) 원칙과도 충돌하지 않는다 — 이 색은 "위험/삭제"라는 새 시맨틱 카테고리가 아니라, 이미 있는 단일 accent 색을 그대로 가져다 쓰는 것이기 때문이다.
- 배경: `colors.accent`
- 아이콘(`trash`, SF Symbol): `colors.surface`
- accessibilityLabel: "삭제"

### 색상 결정: 정적 지도 미리보기 마커는 `pin`이 아니라 `pinSoft`

DESIGN.md 2026-08-31 갱신 이후 `colors.pin`(진행 중 확인 핀 + 지도 마크)과 `colors.pinSoft`(저장된 체크인 핀 + 이동 궤적선)가 분리됐다. 상세화면에서 보여주는 체크인은 항상 이미 저장이 끝난 과거 기록이므로(현재 확인 중인 체크인이 아님), Today 뷰의 "저장된 핀" 규칙과 동일하게 `pinSoft`를 쓴다 — 같은 체크인이 화면마다 다른 색으로 보이는 드리프트를 막기 위한 일관성 결정.

### iOS 네이티브 컴포넌트 기본값 함정 — Alert 버튼 빨강 스타일 회피

iOS `Alert.alert`의 `style: 'destructive'` 버튼은 시스템이 자동으로 빨간 텍스트를 렌더링한다 — Phase 4가 발견한 "탭바 기본 파란 틴트" 함정과 동일한 종류의, 놓치기 쉬운 플랫폼 기본값이다. DESIGN.md의 "UI 전역에서 빨강 계열(semantic 색상) 금지" 원칙을 지키려면 **미저장 경고 다이얼로그의 "저장하지 않고 나가기" 버튼에 `style: 'destructive'`를 지정하지 않는다** — 기본(`style: 'default'`) 스타일만 사용, 버튼 순서와 문구로만 구분한다.

## Screen & Component Notes

### 레이아웃 구조 (위→아래, 고정 순서 — REQ-checkin-detail-layout)

**주 시각적 앵커:** 이 화면은 단일 지배적 포컬 포인트를 두지 않는다 — 시간 → 지도 → 딥링크 → 사진 → 메모라는 고정된 위→아래 읽기 순서 자체가 위계다(REQ-checkin-detail-layout). 굳이 하나를 꼽는다면 **정적 지도 미리보기**가 화면 진입 직후 가장 먼저 시선을 붙잡는 시각적 앵커 역할을 한다 — 전체 너비를 쓰는 유일한 그래픽 블록이며, 텍스트 위주인 시간/딥링크 라인과 대비를 이루는 첫 색상 면적이기 때문이다. 다만 이는 "지배적 focal point를 의도적으로 설계했다"는 의미가 아니라, 고정 순서 레이아웃에서 자연히 가장 눈에 띄는 요소를 확인한 것뿐이다 — 사진이 있으면 지도보다 큰(최대 240px) 이미지 블록이 뒤따르므로 지도는 "유일한" 앵커가 아니라 "첫 번째" 앵커에 가깝다.

```
Stack.Screen (push, 탭바 노출 유지 — product-design.md 네비게이션 셸 다이어그램)
└── 체크인 상세화면 (colors.background, ScrollView, 좌우 패딩 spacing.lg)
     ├─ 헤더: iOS 시스템 기본 네비게이션 바, 타이틀 = 로컬 날짜(예: "8월 31일"), 뒤로가기 버튼이
     │        미저장 경고 다이얼로그 트리거 지점
     ├─ 1. 시간 — typography.timestamp, tabular-nums, 단독 한 줄
     ├─ (spacing.lg)
     ├─ 2. 정적 지도 미리보기 — 전체 너비, 높이 160px, radius.md, colors.pinSoft 단일 teardrop
     │       마커, 스크롤/줌/팬 비활성(인터랙션 없음, 탭해도 아무 동작 없음 — 아래 지도 열기
     │       버튼과 역할 분리)
     ├─ (spacing.sm)
     ├─ 3. "지도 앱에서 열기" — 텍스트 버튼, colors.textMuted, typography.placeName, 좌측 정렬,
     │       최소 44pt 터치 높이
     ├─ (spacing.lg)
     ├─ 4. 사진 — 있으면 전체 너비 이미지(비율 유지, 최대 높이 240px, radius.md) + 우상단
     │       삭제 아이콘 배지(colors.surface 반투명 원형 배경 + colors.textMuted trash 아이콘,
     │       spacing.xs 인셋). 사진 본체를 탭하면 액션시트(촬영/앨범) — 없으면 160px 빈 슬롯
     │       (colors.surfaceSoft 배경, colors.line 1px 테두리, 중앙 카메라 아이콘 + "사진 추가")
     ├─ (spacing.lg)
     └─ 5. 메모 — typography.journalEntry TextInput, multiline, minHeight 96px, colors.surface
             배경, placeholder colors.textFaint. dirty 상태는 화면 로컬 state로만 추적(자동저장
             없음, 위 "저장 트리거 매트릭스" 참고). 저장 실패 시 CheckinActionCard SAVE_FAILED
             패턴(헤드라인+보조문구+다시 시도) 재사용, 메모 영역 바로 아래 인라인 표시
```

**구현 시 확인 필요(설계 계약이 아니라 배치 검증 항목):** expo-router의 `beforeRemove`(또는 동급) 이벤트가 하드웨어 스와이프 백 제스처와 헤더 뒤로가기 버튼 탭 둘 다를 가로챌 수 있는지 계획 단계에서 확인할 것 — 둘 중 하나라도 경고 없이 새는 경로가 있으면 D-01이 깨진다.

### 정적 지도 미리보기

- 렌더링 방식(react-native-maps `scrollEnabled=false` vs 스냅샷 API)은 05-CONTEXT.md Claude's Discretion — 연구/계획 단계에서 확정. 이 UI-SPEC은 **시각적 결과**만 계약한다: 전체 너비, 160px 고정 높이, radius.md, 인터랙션 없음(스크롤/줌/팬/탭 전부 비활성), 마커 1개(`colors.pinSoft` teardrop, Phase 3/4에서 이미 쓰는 28×34px -45도 회전 기법 재사용).
- 지도 스타일(땅/도로/물 색상)은 기존 `colors.mapLand`/`mapRoad`/`mapWater` 그대로 — 이 phase가 지도 스타일을 새로 정의하지 않는다.

### 사진 교체/삭제 (D-03, D-04)

- 교체: 사진 본체 탭 → 기존 액션시트(`ActionSheetIOS`, Phase 3에서 이미 구현) 재사용, "사진 촬영"/"앨범에서 선택".
- 삭제: 별도의 작은 아이콘 배지(사진 우상단 오버레이) 탭 → **확인 없이 즉시** `photo_path`를 null로 갱신하고 화면을 빈 슬롯 상태로 되돌림. undo 없음(D-04) — 체크인 전체 삭제의 4초 스낵바와 명확히 다른, 가벼운 편집 액션.
- 사진 교체 시 기존 파일 삭제 타이밍(새 파일 저장 성공 후 삭제 vs 즉시 삭제)은 05-CONTEXT.md Claude's Discretion — 연구/계획 단계에서 확정, 이 UI-SPEC은 사용자 대면 시각/문구만 계약.

### 수정 저장 실패 UI

- `CheckinActionCard`의 SAVE_FAILED 분기(헤드라인 "저장하지 못했어요" + 보조문구 "저장 공간을 확인해주세요" + "다시 시도" 버튼)와 시각적으로 동일한 카드를 상세화면 메모 섹션 아래 인라인으로 재사용. 컴포넌트 자체를 그대로 import해 재사용할지, 동일 스타일을 복제한 새 컴포넌트를 만들지는 05-CONTEXT.md Claude's Discretion — 연구/계획 단계에서 확정(이 UI-SPEC은 시각적 동일성만 계약).
- `checkinRepo.ts`의 `runWithSingleRetry` + `updateCheckinNoteAndPhoto`를 그대로 재사용(파일 주석에 이미 Phase 5용으로 설계됨이 명시돼 있음) — 자동 재시도 1회 → 실패 시 위 카드 표시.

### 스와이프 삭제 (`CheckinListRow`, `TodayBottomSheet` 리스트)

- 왼쪽 스와이프로 오른쪽에서 삭제 어포던스 노출(iOS 표준 스와이프 방향).
- 어포던스: 폭 72px, 배경 `colors.accent`, 중앙 `trash` SF Symbol(`colors.surface`), accessibilityLabel "삭제".
- 스와이프가 임계값을 넘으면 삭제 확정(별도 확인 다이얼로그 없음, iOS 네이티브 스와이프 삭제 관례) → 리스트에서 즉시 사라짐 + 4초 스낵바.
- 메모/사진 유무와 무관하게 모든 체크인에 동일 적용(REQ-checkin-swipe-delete, "빈 체크인 예외 없음" 확정 사항).

### Undo 스낵바

- 위치: 화면 하단, 탭바 위(오늘 뷰가 탭바 노출 화면이므로 탭바를 가리지 않음).
- 배경: `colors.textPrimary`(어두운 필, 기존 `primaryButton` 배경과 동일 색 재사용 — 새 색 없음).
- 텍스트: `colors.surface`, `typography.placeName`. 좌측 "삭제했어요", 우측 "실행취소"(밑줄, 탭 가능, 최소 44pt 히트 영역).
- 지속시간: 4000ms 정확히(REQ-checkin-swipe-delete). 타임아웃 도달 시 조용히 사라지고 삭제가 최종 확정(DB에서도 실제 삭제 실행 — 스와이프 시점엔 UI에서만 사라지고 DB 삭제는 4초 타이머 만료 시점에 실행하는 "지연 삭제" 패턴 채택 권장, 정확한 커밋 타이밍은 연구/계획 단계 판단).
- 크로스페이드/슬라이드 등 등장·퇴장 모션은 `motion.saveStateCrossfadeMs`(180ms) 재사용 — 새 모션 토큰 발명 없음.

### `CheckinListRow` 탭 가능 전환

- Phase 4에서 순수 `View`였던 컴포넌트를 `Pressable`로 감싼다(D-03 04-CONTEXT.md 뒤집기, 이번 phase가 명시적으로 의도한 변경).
- 탭 피드백: iOS 표준 하이라이트(배경 살짝 어두워짐, `colors.surfaceSoft` 정도) — 새 리플/그림자 효과 발명 안 함.
- 시각적으로 탭 가능함을 처음 암시하는 요소를 화살표(">")나 chevron으로 추가할지는 05-CONTEXT.md에 명시 없음 — **기본값으로 chevron 추가하지 않는다**(스와이프 삭제 어포던스와 시각적으로 섞이지 않게, 리스트 밀도 유지). 탭 가능성은 표준 iOS 하이라이트 피드백만으로 전달.
