`src/notifications/scheduling.ts`의 스텁을 실제 구현으로 채운다.

상수: `CHECKIN_HOURLY_ID = 'checkin-hourly'`, `EVERY_3H_HOURS = [0, 3, 6, 9, 12, 15, 18, 21] as const`, `DAILY_REFLECTION_ID = 'daily_reflection'`. 3시간마다 id 생성기는 `checkin3hId(hour) => \`checkin-3h-${hour}\`` — 배열 인덱스(0~7)가 아니라 **시각 값**(0,3,6,…,21)을 붙인다. 02-RESEARCH.md Summary 문단은 `checkin-3h-0`~`checkin-3h-7`로, Pattern 2 코드 예시는 `checkin-3h-${hour}`로 서로 다르게 적혀 있는데, 실제 코드 예시(Pattern 2)를 정본으로 채택한다 — id에 발화 시각이 그대로 드러나 디버깅 로그가 읽히기 때문이다. 이 결정을 주석으로 남긴다.

`ALL_MANAGED_IDS`: `[CHECKIN_HOURLY_ID, ...EVERY_3H_HOURS.map(checkin3hId), DAILY_REFLECTION_ID]` — 총 10개. 이 배열의 의미("이 앱이 소유해 취소할 권한이 있는 id의 전체 우주")를 주석으로 명시한다. 취소 로직은 절대 이 집합 밖의 id를 건드리지 않는다.

`expectedCheckinIds(frequency)`: `'hourly'` → `[CHECKIN_HOURLY_ID]`, `'every3h'` → `EVERY_3H_HOURS.map(checkin3hId)`, `'off'` → `[]`. `NotificationFrequency`가 닫힌 유니온이므로 런타임 검증 라이브러리를 도입하지 않는다(02-RESEARCH.md Security Domain V5).

`expectedNotificationIds(settings)`: `expectedCheckinIds(settings.checkinFrequency)` + (`settings.dailyReflectionEnabled`이면 `[DAILY_REFLECTION_ID]`, 아니면 `[]`).

`triggerFor(id, settings)` (모듈 내부): id별로 캘린더 트리거 입력을 만든다. `CHECKIN_HOURLY_ID` → `{ type: CALENDAR_TRIGGER_TYPE, minute: 0, repeats: true }` — `hour` 키를 **넣지 않는다**. iOS `UNCalendarNotificationTrigger`는 지정하지 않은 컴포넌트를 와일드카드로 매칭하므로 minute만 지정하면 매시간 정각에 반복 발화한다. `hour: undefined`를 명시적으로 넣는 것도 금지한다 — 테스트가 `toEqual`로 키 부재를 검증한다. `checkin-3h-<h>` → `{ type: CALENDAR_TRIGGER_TYPE, hour: h, minute: 0, repeats: true }`. `DAILY_REFLECTION_ID` → `{ type: CALENDAR_TRIGGER_TYPE, hour: settings.dailyReflectionHour, minute: 0, repeats: true }`.

`contentFor(id)` (모듈 내부): `DAILY_REFLECTION_ID`면 `NOTIFICATION_CONTENT.dailyReflection`, 아니면 `NOTIFICATION_CONTENT.checkin`. 문구 문자열을 이 파일에 인라인으로 쓰지 않는다.

`scheduleById(id, deps)`: `deps.scheduleNotificationAsync({ identifier: id, content: contentFor(id), trigger: triggerFor(id, settings) })`. 커스텀 identifier가 그대로 존중된다는 사실이 이 모듈 전체 설계의 전제임을 주석으로 명시한다(02-RESEARCH.md가 `expo/expo` 소스 `request.identifier ?? uuid.v4()`에서 확인).

`applyNotificationSettings(settings, deps)`: migrations.ts의 "라이브 상태를 먼저 읽고 → 델타를 계산하고 → 델타만 적용한다" 형태를 그대로 따른다. 순서: (1) `deps.getAllScheduledNotificationsAsync()`로 실제 등록 id 집합을 읽는다. (2) `expected = new Set(expectedNotificationIds(settings))`. (3) 취소 대상 = 실제 집합 ∩ `ALL_MANAGED_IDS` − `expected` → 각각 `deps.cancelScheduledNotificationAsync(id)`. 취소를 등록보다 **먼저** 수행한다(Pitfall 4 — 빈도 전환 중 이전 빈도 트리거가 고아로 남는 것을 방지). (4) `expected`의 각 id를 `scheduleById`로 등록한다. 동일 id 재등록은 iOS에서 교체 동작이므로 멱등하다.

각 단계에 해당 pitfall 번호를 인용하는 주석을 단다. 프로미스를 조용히 삼키지 않는다 — 실패는 호출자에게 전파하고(이 모듈은 catch 하지 않는다), 로깅은 Plan 05의 오케스트레이터가 담당한다는 것을 주석으로 명시한다.
