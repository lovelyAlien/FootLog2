`src/notifications/permissions.ts`의 스텁을 구현으로 채운다.

`PermissionSnapshot`은 `status`/`granted`/`canAskAgain` 세 필드만 갖는다. `fetchNotificationPermission`은 `deps.getPermissionsAsync()` 결과에서 이 세 필드만 뽑아 새 객체로 반환한다 — `ios` 등 플랫폼 전용 필드를 통과시키지 않는다. 02-RESEARCH.md Anti-Patterns가 명시한 대로 `ios.status`(IosAuthorizationStatus enum) 기준 분기를 하지 않으며, 왜 표준 필드로 충분한지(PROVISIONAL/EPHEMERAL은 이 앱이 요청하지 않는 옵션이라 등장하지 않음)를 주석으로 남긴다.

`requestNotificationPermission`은 먼저 `deps.getPermissionsAsync()`로 현재 상태를 읽고, `status !== 'undetermined'`면 그 스냅샷을 그대로 반환하고 즉시 종료한다(가드절 — migrations.ts의 early-return 형태). `undetermined`일 때만 `deps.requestPermissionsAsync({ ios: { allowAlert: true, allowSound: true, allowBadge: true } })`를 호출한다. 이 가드가 왜 있는지(iOS는 이미 거부된 상태에서 재호출해도 프롬프트를 띄우지 않고 현재 상태만 반환 — 그래서 priming 화면이 먼저 필요하다)를 주석으로 명시한다.

`shouldShowDeniedBanner(permission)`: `permission !== null && permission.status === 'denied'`. `granted === false`가 아니라 `status === 'denied'`로 판정한다 — `undetermined`도 `granted: false`지만 배너 대상이 아니기 때문이다. 이 구분을 주석으로 남긴다.

priming 세션 플래그: 모듈 레벨 `let primingDismissedThisSession = false`와 `markPrimingDismissed()`/`resetPrimingSession()`. `shouldShowPriming(permission)`은 `permission !== null && permission.status === 'undetermined' && !primingDismissedThisSession`. 다음 사실을 헤더 주석에 명시한다 — 이 플래그는 **의도적으로 영속화하지 않는다**. 02-RESEARCH.md Architectural Responsibility Map이 "Phase 2는 하드코딩 상수, 영속화는 Phase 6/7"으로 못박았고 CONTEXT.md D-01이 설정 영속화를 Phase 6으로 연기했기 때문이다. 플래그의 1차 목적은 UX 선호가 아니라 정확성이다: 이게 없으면 "나중에" 탭 시 index → priming 리다이렉트가 무한 루프를 돈다. 앱을 완전히 종료했다 다시 켜면 권한이 여전히 `undetermined`인 한 priming이 다시 노출되며, 이 동작을 영속 플래그로 바꿀지는 Phase 4(REQ-onboarding-empty-state)에서 재검토한다.

`AppStateLike` 타입을 이 파일에 정의한다(`Pick<typeof AppState, 'addEventListener'>`를 쓰지 않는다 — `react-native`를 타입으로라도 끌어오면 node 환경 테스트에서 해석 부담이 생긴다. 필요한 메서드만 구조적으로 선언한다). `subscribeToForegroundActive(handler, appState = AppState)`는 `appState.addEventListener('change', s => { if (s === 'active') handler(); })`를 등록하고 `() => sub.remove()`를 반환한다. `react-native`의 `AppState`는 이 파일에서만 import 한다.

`useNotificationPermissionBanner()`는 조립만 하는 얇은 훅으로 구현한다: `useState<PermissionSnapshot | null>(null)`, `useCallback`으로 감싼 `recheck`가 `fetchNotificationPermission(defaultNotificationDeps)`를 호출해 상태를 갱신하되 `src/app/index.tsx`와 동일한 `isMounted` 가드를 적용하고 `.catch`에서 `console.error`로 남긴다(프로미스를 조용히 삼키지 않는 repo 규약). `useEffect`에서 마운트 시 1회 `recheck()` 하고 `subscribeToForegroundActive(recheck)`를 구독한 뒤 클린업에서 해제한다. 반환값은 `{ showBanner: shouldShowDeniedBanner(permission), openSettings: () => Linking.openSettings() }`. `Linking`은 `expo-linking`에서 import 하며 `Linking.openURL('app-settings:')`를 직접 쓰지 않는다(02-RESEARCH.md Don't Hand-Roll).

TDD 순서를 지킨다: 16개 테스트를 통과시키는 최소 구현만 작성한다.
