## Problem Statement
반복되는 일상 속에서 사람들은 자신이 어디를 가고 있는지조차 인지하지 못한 채 무의식적으로 같은 곳만 오간다. 새로운 곳, 낯선 모험을 꿈꾸면서도 정작 삶을 살아가다 보면 그 마음을 쉽게 잊는다. FootLog는 매시간 알림으로 사용자가 자신의 위치를 의식적으로 확인·기록(체크인)하게 하고, 이를 하루/주 단위로 모아 "반복되는 동선"과 "새로 가본 곳"을 담담하게, 판단 없이 보여줌으로써 탐험 욕구를 자연스럽게 불러일으키는 도구다. 체크인마다 사진/메모를 남겨 시간과 공간이 엮인 개인 기록(저널)으로도 기능한다.

## Demand Evidence
- 퇴사 후 구직 활동 중, 카페에서 반복적으로 작업하며 늘 가던 곳만 다니고 새로운 곳을 찾기 어려웠던 구체적 경험 (창업자 본인의 실제 계기).
- 반복되는 하루하루로 인해 시간이 더 빠르게 흐른다고 느낌 — 순간의 기억/추억을 기록으로 남기고 싶은 욕구.
- 현재 수기로 일기를 쓰고 있으나 "자주 까먹어서 빼먹은 적이 많음" — 명확한 미충족 니즈(기록 습관의 실행력 부재).

## Status Quo
수기 일기. 시작 트리거가 스스로의 판단에 의존하기 때문에 자주 잊어버리고 건너뛴다. Google 타임라인 같은 완전 자동 위치 기록 서비스도 존재하지만, 수동적 기록이라 "의식적 자각"이나 "그 순간의 생각/감정 기록"을 만들어내지 못한다 (창업자가 직접 사용하지 않고 있음).

## Target User & Narrowest Wedge
- 타겟 유저: 현재는 창업자 본인이 유일한 확인된 타겟. 외부 검증된 유저는 없음 (세션 중 명시적으로 확인됨).
- 가장 좁은 웨지: "알림 → 체크인(위치 캡처 + 확인 핀 탭 + 선택적 메모/사진) → 지도/리스트로 오늘 기록 보기." (2026-08-23, /autoplan CEO 리뷰 — 문구 정정: 원래 "원탭"이라 썼으나, 2026-08-22 "체크인 진입점 통합" 개정으로 실내 오탐 방지를 위해 확인 핀 단계가 항상 끼어들어 최소 2탭이 됨. Codex/Claude 아웃사이드 보이스 둘 다 독립적으로 이 불일치를 지적 — 데이터 정확성을 위해 의식적으로 받아들인 트레이드오프이므로 플로우는 그대로 두고 웨지 설명 문구만 실제 플로우에 맞게 수정.) 그 외 기능(주간 반복 패턴 분석, 하루 리뷰 글쓰기)은 이 핵심 루프가 검증된 뒤에 의미가 있다.

## Constraints
- 개인 학습/포트폴리오 목적도 겸함 — Kotlin/Spring Boot 백엔드 실전 경험이 목적 중 하나 (창업자 확인).
- 매시간 안정적으로 푸시를 보내려면 실제 모바일 앱(React Native/Expo)이 필요 — 일반 웹사이트로는 불가능.
- iOS 알림 인프라(APNs) 및 배터리/권한 이슈 고려 필요.
- **Apple Developer 계정 — 해소됨 (2026-08-24, `/superpowers:brainstorming`):** EAS Dev Client를 무료 "Personal Team" Apple ID로 빌드하면 프로비저닝 프로파일이 7일마다 만료돼 앱이 안 켜지게 되는 문제가 2026-08-23 Eng 리뷰에서 발견됐었음. 이번 브레인스토밍 세션에서 한 단계 더 파고든 질문(주간 재빌드가 로컬 SQLite 데이터를 보존하는지)까지 포함해 **창업자가 이미 유료 Apple Developer Program($99/년)에 가입되어 있음을 확인** — 프로비저닝 프로파일이 1년 유효해 주간 재빌드 자체가 발생하지 않으므로, 이 리스크(및 파생 질문인 "재빌드가 데이터를 지우는가")는 해당 없음으로 종결. 참고로 기술적으로는 같은 번들 ID 위에 덮어쓰는 업데이트 설치라면 iOS 샌드박스 데이터 컨테이너(SQLite/사진)가 보존되지만(앱스토어 업데이트와 동일 매커니즘), 이번 결정으로 실기기 검증 자체가 불필요해짐.

## Premises
1. 핵심 가치는 위치를 자동으로 기록하는 것이 아니라, 의식적으로 멈춰서 알아차리고 사진/메모를 남기는 행위 자체다 — Google 타임라인이 이미 자동 기록을 무료로 제공하므로.
2. (Codex 검토 후 수정됨) 성공 지표는 체크인 완료율 단독이 아니라 **체크인 완료율 + 메모/회고 작성률**을 함께 봐야 한다. 완료율만 높고 내용이 비어있는 건 실패로 간주한다. (브레인스토밍 리뷰 후 재수정, 2026-08-21) 목표가 빠른 개발/서비스화로 조정되며 완료율에 대한 정량적 수치 목표는 제거하고, 1~2주 실사용 후 "실제로 습관이 됐고 계속 쓸만한지"를 창업자 본인이 정성적으로 판단하는 것으로 대체 — 자세한 내용은 Success Criteria 참고.
3. "매시간 무조건" 알림은 며칠 안에 무시당할 가능성이 높다 — 알림 주기, 방해금지 시간, 스누즈 설계가 필요하다.
4. (office-hours에서 재정의 → eng-review에서 Codex 아웃사이드 보이스 반영 후 원안으로 회귀) 원래 전제: "개인용 MVP 우선, 사업화 인프라에 시간 쓰지 말자." office-hours에서 학습 목적으로 한 차례 뒤집혔으나, eng-review에서 "1단계가 검증이 아니라 풀스택 개발이 됐다"는 Codex의 지적에 창업자가 동의해 **원래 전제대로 최종 확정**: 1단계는 백엔드 없이 로컬 전용, Kotlin/Spring Boot 학습은 2단계로 이동.
5. 매시간 푸시 알림을 신뢰성 있게 보내려면 사실상 모바일 앱(React Native/Expo)이 필요하다.
6. "담담하게, 판단 없이" — 반복성을 보여주는 톤은 죄책감·연속기록(streak) 압박이 없어야 한다. 전제라기보다 제품 톤 원칙이지만, UI/카피 결정에 지속적으로 적용되어야 한다.

## Cross-Model Perspective
Codex(GPT-5.5, 독립 검토)의 핵심 진단: 이 제품은 "위치 트래커"가 아니라 "일기 실행력(adherence) 도구"다. 가장 결정적 근거는 "수기로 일기를 쓰고 있지만 자주 까먹는다"는 창업자의 답변. Codex는 성공 지표를 "체크인 완료율"에서 "체크인이 실제로 간직할 만한 기억/자기인식을 만들어내는가"로 확장할 것을 제안했고, 이를 반영해 전제 #2를 수정했다. "하루 리뷰(지도 재구성+글쓰기)" 기능은 체크인을 나중에 보람있게 만들어줄 때만 전제 #2를 지지하며, 강제하면 오히려 해친다는 지적도 있었다 — 선택적 마무리로 취급할 것을 권고. 48시간 프로토타입 제안: Expo React Native + expo-notifications/expo-location/expo-sqlite/expo-image-picker/react-native-maps, 로컬 전용(백엔드 없음), 계정/클라우드동기화/패시브추적/소셜기능/AI요약 제외. (창업자는 이후 세션에서 Spring Boot Kotlin 백엔드를 의식적으로 추가하기로 결정 — Codex 권고와 다른 방향.)

## Approaches Considered
### Approach A: 로컬 전용 최소기능 앱
Expo/React Native, 클라우드 없음. 알림→체크인→지도/메모만 구현. 검증 속도 최우선. (Effort: S, Risk: Low)

### Approach B: 사업화 대비 구조 (React Native + 클라우드 백엔드)
초기부터 클라우드 동기화, 추후 멀티유저/계정 지원 가능한 구조. (Effort: L, Risk: Med — 전제 #4 원안과 충돌)

### Approach C: 노코드 검증
코드 없이 iOS 캘린더 반복 알림 + 메모 앱 조합으로 핵심 가설(체크인 완료율)만 먼저 검증. 온전한 검증은 1주일이 이상적이지만, 최소 3일이면 "이 리듬에 전혀 반응 안 한다" 같은 강한 부정 신호는 충분히 잡을 수 있다. (Effort: XS, Risk: Low)

## Recommended Approach
**최종 확정 (Codex 아웃사이드 보이스 반영, 두 번째 반전):** 1단계는 **Approach A — 로컬 전용 최소기능 앱**으로 확정한다. Spring Boot(Kotlin) 백엔드, 카카오 OAuth2/PKCE 인증, S3 사진 업로드는 전부 **2단계로 이동**한다.

**결정의 경과 (참고용, 뒤집힌 순서를 남겨둠):**
1. office-hours: 창업자가 학습/포트폴리오 목적으로 Spring Boot 백엔드를 1단계부터 포함하기로 결정 (전제 #4 재정의).
2. eng-review 초반: 백엔드가 인터넷에 노출되므로 카카오 OAuth+PKCE 인증을, 무기한 사진 보관 때문에 S3 업로드를 각각 1단계에 추가 결정.
3. eng-review 후반 (Codex 아웃사이드 보이스): "1단계가 더 이상 MVP가 아니라 풀스택 개발이다. 검증 전 인프라 구축 리스크를 인지했다면서 실제로는 그 리스크를 선택했다"는 지적에 창업자가 동의 — **Codex의 원래 제안(로컬 전용)으로 회귀**.

Spring Boot/Kotlin 학습이라는 목적 자체는 유효하지만, 그 학습은 **2단계에서** — 핵심 루프(알림→체크인→로컬 기록)가 실제로 며칠 이상 쓰이는지 검증한 뒤에 — 하기로 한다. 학습 목적이 제품 검증 속도를 잡아먹지 않도록 순서를 분리한 것.

**1단계 (핵심 루프, 로컬 전용):** Expo React Native, 클라우드/백엔드 없음. `expo-notifications`(로컬 알림) / `expo-location` / `expo-sqlite` / `expo-image-picker` / `react-native-maps`. 알림→체크인(위치+선택적 사진/메모)→SQLite 저장→오늘 목록/지도 뷰.

**빌드 방식 (기술적으로 확정, 선택의 여지 적음):** `react-native-maps`는 네이티브 코드가 필요해 Expo Go로는 실행이 안 되고 **EAS Dev Client**(개인 계정 무료 빌드)가 필요하다. 이건 백엔드 유무와 무관한 기술적 제약이라 재검토 없이 그대로 반영.

**오프라인 처리 (유지):** 체크인은 항상 먼저 SQLite에 즉시 저장(그 순간 "저장 완료" 표시). 1단계엔 동기화할 백엔드가 없으므로 이 결정은 오히려 더 단순해짐 — 로컬 저장이 곧 최종 저장.

**알림 스케줄링 — 반복 트리거 방식으로 전환 (재정정, 2026-08-22 — /plan-eng-review Step 0):** 이전 버전(브레인스토밍 리뷰, 2026-08-21)은 "iOS 로컬 알림 최대 64개 대기 한도" 때문에 개별 알림을 매일 재스케줄링하는 방식(방법 B)을 채택했었음. 오늘 eng review에서 재검토한 결과, **방법 A(반복 캘린더 트리거, `repeats: true`, `minute`만 지정)로 전환** — 이렇게 하면 "매시간"은 트리거 1개, "3시간마다"는 최대 8개(0,3,6,...21시)로 표현되어 64개 한도에 애초에 걸리지 않고, 매일 재스케줄링 로직 자체가 불필요해짐. **알림 빈도 설정**(매시간 / 3시간마다 / 끔, SetLog 실측 확인)은 그대로 유지, 방해금지 시간은 여전히 OS Focus/DND에 위임(앱이 직접 계산 안 함).

**트레이드오프 (인지하고 감수) — 단, 최소 자가진단은 추가 (2026-08-23 재정정, Eng 리뷰):** iOS 반복 트리거가 실전에서 하루 이틀 뒤 조용히 안 울리게 되는 사례가 문서화되어 있음([expo/expo#18068](https://github.com/expo/expo/issues/18068), [Apple Developer Forums](https://developer.apple.com/forums/thread/670622)). 방법 B는 "앱 열 때마다 재확인·재생성"하는 구조라 이런 이상 상태를 스스로 고치는 자가 치유 성질이 있었지만, 방법 A는 트리거 하나에 걸어두고 이후 확인 로직이 없어 조용히 멈춰도 알아챌 방법이 없었음 — 개인용 도구이고 관리 단순함(매일 재스케줄링 로직·64개 한도 관리 전부 불필요)이 신뢰성 리스크보다 크다고 판단해 방법 A로 전환한 결정 자체는 유지. **다만 CEO 리뷰(Codex)와 Eng 리뷰(Codex)에서 같은 gap을 두 차례 독립적으로 지적함 — "체크인을 안 한 것"과 "알림이 멈춘 것"을 구분할 방법이 전혀 없으면 1~2주 실사용 검증 자체의 해석 가능성이 흔들림. 방법 B로 되돌리는 재스케줄링 로직 부활 없이(그 복잡도 회피가 방법 A 전환의 핵심 이유였으므로), 앱이 포그라운드로 돌아올 때마다(기존에 알림 권한/위치 권한 재확인에 쓰는 것과 같은 `AppState` 훅) 예약된 트리거가 실제로 등록돼 있는지 가볍게 조회하고, 사라졌으면 조용히 재생성하는 최소 자가진단만 추가하기로 확정** — 이건 매일 반복 재스케줄링(방법 B의 복잡도)이 아니라 "가끔 확인하고 없으면 다시 건다"는 훨씬 가벼운 안전장치라 방법 A의 단순함을 크게 해치지 않음. T2에 반영.

**알림 스케줄 테이블 — 폐기됨 (2026-08-22, 재브레인스토밍에서 발견된 더 근본적인 전제 차이로 불필요해짐):** 이 테이블(notification_schedule, 06:00~24:00 슬롯 계산 등)은 "체크인은 알림 시각에 묶인 슬롯"이라는 전제 위에서만 필요했음. 아래 "체크인 모델 — 자유형으로 재정의"에서 그 전제 자체가 틀렸다는 게 밝혀져 전체 폐기. 알림은 순수 리마인더일 뿐이고, 체크인은 항상 실제 발생 시각으로 기록되는 독립 이벤트라 "예정 시각과 비교"할 대상 자체가 없어짐 — 체크인 테이블 하나로 충분.

**체크인 모델 — 자유형으로 재정의 (확정, 2026-08-22, 사용자가 오늘 세션 전체의 슬롯 기반 설계와 다른 원래 기획을 제시):**
1. 체크인은 알림에 묶인 "슬롯"이 아니라, 언제든 자유롭게 발생하는 독립적인 이벤트다. 알림은 순수 리마인더일 뿐 체크인의 필수 조건이 아니다 — 알림 없이도 앱을 열어 그때그때 체크인할 수 있다.
2. 리스트에 보이는 시간은 항상 **실제 체크인한 시각**이다(예: 9시 알림 → 9시 15분에 체크인 → 화면엔 "09:15"로 표시). 알림이 온 시각이 아니다.
3. 이 두 전제 때문에 "슬롯"이라는 개념 자체가 존재하지 않는다 — 채울 빈 자리도, 지켜야 할 예정 시각도 없다. 이번 세션에서 슬롯 모델 위에 쌓았던 것(알림 스케줄 테이블, 빈 슬롯 시각 문법, 소급 체크인 엄격 금지, 06:00~24:00 슬롯 생성 창)은 전부 이 재정의로 대체·폐기됨 — 상세는 아래 각 항목 참고.

**스누즈 기능 제거 (2026-08-22):** 방법 A로 전환하며 스누즈("10분 후" 알림 미루기) 기능을 함께 제거하기로 결정 — 반복 트리거 하나로 관리하는 구조에서 스누즈를 넣으려면 결국 일회성 트리거를 별도로 관리해야 해서(정각 트리거 옆에 스누즈용 개별 트리거가 나란히 필요), 방법 A의 "트리거 1개로 단순화"라는 이점이 퇴색됨. 아래 "스누즈 UX" 항목은 폐기됨 — 상세는 해당 항목 참고.

**GPS/실내 정확도 (브레인스토밍 리뷰 후 수정, 2026-08-21):** Codex가 지적한 대로 카페·지하철 등 실내에서는 GPS가 부정확할 수 있다. 최초 대응안이었던 "이전 체크인과 같은 장소" 버튼은 실내에 오래 머물 때 반복 사용되면서 실제 이동을 감춰 위치 데이터를 왜곡시킬 위험이 있다고 판단해 폐기 — 대신 GPS 실패/저정확도 시 **드래그 가능한 지도 핀**으로 전환한다: 기본 위치(마지막으로 잡힌 GPS 좌표 또는 이전 체크인 위치)를 핀으로 미리 찍어두고, 맞으면 그대로 "체크인" 확인, 틀리면 손가락으로 핀을 정확한 위치로 옮긴 뒤 확인. 화면 하나·탭 한두 번으로 끝나 여전히 최소 비용이면서 위치 정확도는 훨씬 나아진다. `react-native-maps`가 이미 1단계 의존성이라 draggable marker 기능만 추가하면 되어 별도 검색 UI(수동 장소 검색, 2단계로 여전히 유지)보다 훨씬 가볍다.

**소급 체크인 개념 자체가 사라짐 (2026-08-22 — 위 "체크인 모델 재정의" 참고):** 원래는 "알림을 놓치면 그 시간대는 빈 슬롯으로 남기고 소급 입력은 허용하지 않는다"였으나, 슬롯 자체가 없어지면서 "소급으로 채운다"는 행위 자체가 성립하지 않게 됨(항상 실제 현재 시각으로만 기록되므로, 과거 시각을 골라 입력하는 게 애초에 불가능). Codex가 예전에 "지표 순수성보다 사용자 가치를 우선해야 한다"고 지적했던 부분이, 결과적으로 지표 개념 자체를 없애는 방향으로 해소됨.

## Success Criteria
**1단계 (핵심 루프, MVP) — 이 기준이 충족되어야 2단계로 진행 (브레인스토밍 리뷰 후 정량 → 정성 기준으로 수정, 2026-08-21):**
- 원래는 완료율 %/메모 첨부율 %로 정량 게이트를 뒀으나(아래 이전 버전 참고), 목표가 "빠르게 개발하고 서비스화까지 가보는 것"으로 조정되며 수치 목표는 제거. 대신 **1~2주 실사용 후 창업자 본인이 이 루프(알림→체크인→기록)가 실제로 습관이 됐고 계속 쓸만하다고 느끼는지**를 정성적으로 판단해 2단계 진행 여부를 결정한다.
- **명시적 kill condition — 확정 (2026-08-24 `/gstack-autoplan` — CEO 페이즈 dual voice에서 재발견 후 이 섹션에 직접 반영, T27):** 정성 판단이 "그냥 계속 써보자"는 매몰비용 합리화가 되지 않도록, 아래 조건 중 하나라도 해당하면 2단계로 진행하지 않고 중단한다(자가 판단이 유일한 사용자이자 평가자인 구조라 이 기준을 미리 적어두는 게 특히 중요):

  - **1~2주 전체 기간 동안 메모/사진 첨부율이 체크인의 20% 미만** — 위치만 기계적으로 찍고 회고 내용이 거의 없으면, 전제 #2("완료율만으론 부족")가 우려했던 "속 빈 체크인"이 실현된 것으로 판단.

- (참고, 이전 버전) 완료율이 기존 수기 일기(The Assignment 3일 실측 베이스라인)보다 명확히 높은지, 완료된 체크인의 50% 이상에 메모/사진이 첨부되는지를 수치로 재려 했던 초안 — 정성 판단으로 대체됨.

## Visual Design Decisions (from /plan-design-review, Codex + Claude subagent 합의)

두 독립 AI 모두 같은 결론에 도달: 이 문서는 제품/엔지니어링 결정은 탄탄하지만 실제 화면 디자인(위계, 상태, 톤)이 0이었음. 가장 심각한 지적은 **전제 #6("담담하게, 판단 없이")이 UI 결정으로 한 번도 번역되지 않았다**는 것 — "놓친 알림"을 시간표 형태로 보여주는 순간 그 자체가 이미 판단(실패 신호)이 될 위험이 크다는 지적. 아래는 코드 작성 전 확정한 최소 디자인 스펙.

**체크인 진행 중 탭 전환 (확정, 2026-08-23 `/plan-eng-review` — Codex 지적, 하단 탭바 도입으로 새로 생긴 gap):** 위치 확인→확인 핀→저장→메모/사진 흐름 도중 사용자가 "캘린더" 탭으로 전환하는 걸 막지 않는다. 위치+시간이 SQLite에 저장되기 전(즉 "확인" 탭 이전) 단계에서 탭을 전환하면 그 드래프트는 조용히 사라짐 — 이미 확정된 원칙("저장 성공 전까지는 아무것도 커밋되지 않는다")과 그대로 일치하고, 체크인은 언제든 다시 자유롭게 할 수 있으므로 유실로 취급하지 않는다. 저장 이후(메모/사진 입력 단계)에 탭을 전환해도 체크인 본체(위치+시간)는 이미 저장된 상태라 문제없음 — 메모/사진만 나중에 상세화면에서 추가하면 됨(이미 확정된 "저장 후 메모/사진 수정, 언제든 가능" 원칙과 동일). 탭 전환을 막는 별도 로직 불필요.

**체크인 진입점 통합 (브레인스토밍 리뷰 후 수정, 2026-08-22):** 알림 탭과 앱 아이콘 실행이 서로 다른 첫 화면을 보여주던 기존 설계를 폐기하고, **진입점과 무관하게 항상 오늘 뷰(지도)가 먼저 뜨도록** 통합. 이유는 두 가지 — (1) 전제 #1 "핵심 가치는 의식적으로 멈춰서 알아차리는 행위"에 저장 완료 화면보다 지도(내 위치+과거 핀)를 먼저 보여주는 쪽이 더 부합하고, (2) GPS가 API상 "성공"이라 응답해도 실내·다층 건물 등에서 실제로는 틀린 위치를 반환하는 경우가 있는데, 기존엔 이런 케이스를 accuracy 임계값으로만 걸러 정확도가 "충분히 높다"고 판정되면 그대로 조용히 저장돼버리는 gap이 있었음. 지도를 먼저 보여주고 확인 핀을 항상 거치게 하면 이 gap이 구조적으로 메워짐. 트레이드오프로 완료까지 탭이 최소 1회 늘어나지만(예전: 알림 탭 한 번으로 자동 완료 / 지금: 알림 탭 → 체크인 버튼 → 확인, 최소 2탭), 개인 사용 시나리오에서는 감수 가능한 수준으로 판단.

**체크인 화면 위계 (2026-08-22 개정 — 진입점 통합 반영):**
1. 진입 시 최상단·즉시·크게 — **오늘 뷰(지도)**: 내 현재 GPS 위치 + 오늘 체크인한 핀들. "체크인" 버튼이 화면의 주인공급으로 노출.
2. "체크인" 탭 → 위치 캡처(성공/실패/저정확도 **모두 동일 경로**)를 거쳐 지도 위에 **확인용 드래그 가능 핀**이 뜸(기본 위치 = GPS 캡처 결과, 실패 시 마지막 위치). GPS 정확도와 무관하게 항상 이 확인 단계를 거침 — 예전처럼 "정확도가 높으면 자동 저장"하는 예외 경로 없음. 맞으면 그대로 "확인", 틀리면 드래그로 조정 후 "확인". 드래그로 조정된 체크인은 `locationSource: "gps_dragged"`로 저장되고(2026-08-24 `/gstack-autoplan` Eng 리뷰 — Codex 지적, 이 문장이 실제 스키마 enum에 없는 `"manual"` 값을 쓰고 있던 drift 정정 — 아래 "로컬 데이터 모델 스키마"의 5-값 enum이 정본) 지도/리스트에서 일반 체크인과 시각적으로 살짝 구분 표시(데이터 신뢰도 인지용, 톤은 여전히 담담하게)
3. "확인" 탭 이후 — 캡처 상태/저장 완료 표시 (작은 토스트 아님, 화면의 주인공), 그 바로 아래 메모/사진 입력 영역을 **기본 노출**(접혀있지 않게). 초대하는 듯한 placeholder("지금 여기서 뭘 하고 있나요?"), 빨간 별표나 "필수" 표시 없이 시각적으로 선택사항임을 유지

(참고, 폐기된 이전 결정: "이전 체크인과 같은 장소" 버튼은 실내에 오래 머물 때 반복 사용되며 실제 이동을 감추는 데이터 왜곡 위험이 있어 애초에 폐기했었고, 이번 개정으로 "GPS 실패 시에만" 드래그 핀을 보여주던 조건부 경로도 함께 폐기됨 — 항상 보여주는 단일 경로로 단순화.)

**오늘 뷰 (확정, 이제 앱의 유일한 진입 화면이기도 함):** 지도가 1차 시각적 앵커, 화면 상단 대부분을 차지(2026-08-23 수정 — 아래 "네비게이션" 항목의 하단 탭바 도입으로 완전한 엣지투엣지는 아니게 됨, 하단은 상시 탭바). 리스트/타임라인은 지도 아래 별도 섹션이 아니라 **바텀시트**로 지도 하단 절반 정도를 덮는 형태(Apple Maps/Uber 스타일) — 상단에 드래그 핸들 바가 있어 위로 끌면 리스트가 더 넓게, 아래로 끌면 지도가 더 넓게 보임. "체크인" 버튼은 시트 위 지도 영역에 알약 모양으로 떠 있고, 탭바보다 위 레이어에 위치해 가려지지 않음. **리스트는 오늘 실제로 체크인한 기록만 시간순으로 표시(2026-08-22 재정정 — 체크인 모델 자유형 재정의 참고)** — 슬롯이나 빈 자리 개념 자체가 없으므로, 알림을 놓쳐도 리스트에 아무 흔적이 안 남고(빈 점선도, "+" 도 없음), 체크인이 있을 때만 그 실제 시각으로 한 줄씩 생김. 완료된 행을 탭하면 상세 화면이 열림(메모/사진 수정, 아래 참고). 오늘 아직 체크인이 하나도 없으면 리스트 영역에 옅은 안내 텍스트 한 줄("아직 기록이 없어요")만 표시. 알림 탭이든 앱 아이콘 실행이든 이 화면으로 진입. 목업: `~/.gstack/projects/FootLog2/designs/notif-permission-denied-20260822/variant-B-bottomsheet-v2.png` (단, 목업의 빈 슬롯 점선 표현은 이제 미해당 — 실제 체크인 행만 렌더링)

**알림 권한 거부 시 전체 플로우 (확정, 2026-08-22 — "추가로 스펙 필요" #1 해소):** 최초 실행 시 OS 시스템 권한 팝업을 바로 띄우지 않고, 그 전에 짧은 priming 화면("매시간 알림으로 지금 어디 있는지 잠깐 기록해요" + "알림 허용하기" 버튼)을 먼저 보여준다 — iOS는 시스템 팝업을 한 번 거부하면 앱에서 다시 띄울 수 없고 설정 앱으로만 복구 가능하기 때문. priming에서 "나중에"를 누르거나 OS 팝업에서 거부해도 앱 사용을 막지 않고 그대로 오늘 뷰로 보낸다. 대신 상단 바로 아래 작고 조용한 회색 텍스트 배너("알림이 꺼져있어요 · 설정에서 켜기", 아이콘·경고색 없음)를 노출하고, 탭하면 `Linking.openSettings()`로 iOS 설정의 이 앱 알림 설정으로 이동한다. 이 배너는 전제 #6(담담하게)과 상충하지 않는다 — 사용자 행동(체크인 여부)에 대한 판단이 아니라 시스템 상태 표시(와이파이 꺼짐 표시와 같은 성격)이기 때문에 계속 떠 있어도 된다. 앱이 포그라운드로 돌아올 때마다(`AppState` 변화 감지) 알림 권한 상태를 재확인해 허용으로 바뀌면 배너를 없애고 그 시점부터 알림 스케줄링을 시작하며, 반대로 나중에 설정에서 껐으면 배너가 다시 뜬다. 알림이 꺼진 상태에서도 오늘 뷰의 수동 "체크인" 버튼은 항상 동작하므로 앱 자체가 못 쓰게 되진 않는다 — 다만 습관 형성이라는 제품의 핵심 가치는 약해짐을 인지하고 감수. 목업: `~/.gstack/projects/FootLog2/designs/notif-permission-denied-20260822/variant-B-bottomsheet-v2.png`

**저장 실패 시 사용자 대면 UI (확정, 2026-08-22 — CRITICAL gap 해소):** "확인" 탭 직후 SQLite에 위치+시간 최소 레코드를 쓰는 시점(메모/사진은 아직 입력 전이라 이 시점 실패로는 유실될 콘텐츠가 없음)에 쓰기 실패 시: (1) 조용히 자동 재시도 1회 — 그동안 GPS 로딩 때와 동일한 은은한 인디케이터, 별도 모달 없음. (2) 재시도도 실패하면 "저장 완료"가 뜰 자리에 대신 **"저장하지 못했어요"** + 옅은 회색 보조 텍스트(예: "저장 공간을 확인해주세요") + **"다시 시도"** 버튼 — 빨간색·경고 아이콘 없이 담담한 톤(전제 #6). (3) 저장 성공 전까지 메모/사진 입력 화면은 노출하지 않음 — 순서를 지켜 저장 안 된 상태에서 콘텐츠를 받지 않음. (4) 계속 실패해도 "다시 시도" 버튼은 계속 살아있고, 사용자가 뒤로 가서 화면을 나가려 하면 "이 체크인은 저장되지 않았어요"를 한 번 보여줘 조용히 사라지지 않고 인지된 상태로 남게 함(체크인 자체가 생성되지 않은 채로 — 리스트에도 당연히 안 나타남).

**위치 권한 거부 시 플로우 (확정, 2026-08-23 — CEO/Design 리뷰 둘 다 독립적으로 지적한 critical gap 해소, T19):** 알림 권한과 달리 위치 권한은 priming 화면 없이 첫 "체크인" 탭 시점에 맥락적으로(contextual) 요청된다(위 "첫 실행 온보딩" 참고) — 그만큼 한 번의 실수(무심코 "허용 안 함")로 앱의 핵심 동작이 통째로 막힐 위험이 커서, 알림 거부 플로우와 최소 동급의 스펙이 필요하다.
- **iOS 위치 권한 최초 거부 시:** 체크인 버튼은 계속 화면에 존재(비활성화하거나 숨기지 않음). 탭하면 확인 핀 화면으로 그대로 진입하되, GPS 캡처를 시도하지 않고(권한이 없으면 OS가 마지막 캐시 위치도 내주지 않음 — 2026-08-23 Eng 리뷰에서 정정, Codex 지적: "마지막으로 알려진 위치"를 OS에 요청할 수 있다고 가정한 원안은 틀림) 앱이 자체적으로 기억하는 상태(가장 최근 체크인 위치, 없으면 지도 마지막 표시 좌표, 그마저 없으면 고정 기본 좌표)로 핀을 띄운다. 사용자는 드래그로 직접 위치를 지정해 체크인을 완료할 수 있다("위치 없이는 체크인 불가"가 아니라 "자동 캡처만 불가"). 핀 색/아웃라인은 GPS 폴백과 동일하게 옅게 표시(`locationSource: "manual_denied"`).
- **은은한 상태 배너:** 오늘 뷰 상단, 알림 거부 배너와 같은 자리·같은 톤으로("위치 권한이 꺼져 있어요 · 설정에서 켜기", 아이콘·경고색 없음) — 두 배너가 동시에 뜨면 세로로 스택(알림 배너가 위, 위치 배너가 아래; 둘 다 시스템 상태 표시이지 판단이 아니므로 전제 #6과 상충하지 않음, 위 "알림 권한 거부" 항목 참고). 탭하면 `Linking.openSettings()`로 이동.
- **iOS "Location Services" 전체 꺼짐 vs 앱별 거부 구분 없음(의도적 단순화):** 두 상태 모두 iOS 설정 앱으로 보내는 동일한 딥링크·동일한 배너 문구로 처리 — 개인 도구 규모에서 두 경로를 구분해 서로 다른 설정 화면으로 보내는 복잡도는 이득 대비 과함. 설정 앱에 도착한 뒤 사용자가 알아서 올바른 위치(Location Services 전역 토글 vs 앱별 권한)를 찾는다.

- **사진 첨부 진입 방식 — 카메라+라이브러리 둘 다 허용 (확정, 2026-08-24 `/superpowers:brainstorming`):** 사진 첨부 영역을 탭하면 iOS 표준 액션시트("사진 촬영" / "앨범에서 선택") 노출 — 촬영 전용이 아님. 카메라(`NSCameraUsageDescription`)와 사진 라이브러리(`NSPhotoLibraryUsageDescription`) 두 개의 별도 iOS 권한이 필요하며, 각 권한은 해당 옵션을 실제로 탭한 시점에 맥락 있게(contextual) 요청됨(위치 권한과 동일한 패턴). 실패 인라인 문구는 두 경로 모두 동일하게 재사용 — TODOS.md의 기존 P3 항목("사진 권한 거부 vs 리사이징 실패 문구 분리")이 다루는 케이스가 카메라 거부/라이브러리 거부/리사이징 실패 3가지로 늘어남.

**모션 스펙 (확정, 2026-08-22 — /plan-design-review Pass 4, Codex 지적 hard rule 위반 해소):** 문서에 모션이 전혀 정의되어 있지 않아 구현 시 각 단계마다 임의의 타이밍이 될 위험이 있었음. 짧고 기능적인 모션만 정의(장식적 모션 없음, 담담한 톤 원칙과 일치):

**타겟 기기 명시 — 확정 (2026-08-24 `/gstack-autoplan` Design 리뷰, Codex 지적):** "반응형 해당 없음"이 지금까지 구체적 기기 없이 선언돼 있어, "단일 기기"라는 말이 숨겨진 레이아웃 가정을 감추는 핑계가 될 위험이 있었음(바텀시트+지도+플로팅 버튼+탭바 조합은 작은 화면·큰 텍스트·키보드 열림 상태에서 특히 깨지기 쉬운 레이아웃). 명시: **창업자 본인의 실제 iPhone 기종**(정확한 모델은 T1 착수 시 확정, 목업은 390×844pt 기준 — iPhone 12/13/14/15 표준 크기와 동일)을 타겟으로 함. **Dynamic Type:** 시스템 기본 크기만 지원, 사용자가 접근성 큰 텍스트로 바꾼 상태는 1단계 스코프 밖(창업자 본인이 기본 크기로 사용). **Reduce Motion:** 이미 정의된 모션이 전부 짧고 기능적(220/160/180ms, bounce 없음)이라 Reduce Motion 켜짐 상태에서도 그대로 두어도 무방 — 별도 분기 불필요. **방향:** 세로 모드 전용, 가로 모드 미지원(지도+바텀시트 레이아웃이 세로 전제로 설계됨, 가로 잠금 명시).
- **터치 타겟:** 모든 탭 가능 요소(체크인 버튼, 지도 핀, 리스트 행, 스와이프 삭제, 아이콘 버튼) 최소 44×44px.
- **명도 대비:** 본문 텍스트(메모, 리스트 라벨 등)는 배경 대비 최소 4.5:1 — "옅은 회색 보조 텍스트"(빈 리스트 안내 문구, 배너 문구 등)도 이 기준을 지키는 회색 값으로 선택(웜 그레이 팔레트 확정 시 hex와 함께 검증, DESIGN.md 항목 참고).
- **VoiceOver 라벨:** 아이콘 전용 버튼(햄버거, 캘린더, 체크인 핀 아이콘, 스와이프 삭제)에 명시적 라벨 필요. 지도 핀 자체는 지도가 1차 시각적 앵커이지만 VoiceOver 사용자를 위해 바텀시트의 리스트가 이미 비-지도(non-map) 경로 역할을 함 — 핀 정보(시간/장소명)가 리스트에도 동일하게 텍스트로 존재하므로 **조회(오늘 뷰·과거 날짜 뷰의 핀 열람)에는** 추가 설계 불필요.
- **범위 정정 (2026-08-24 `/gstack-autoplan` Design 리뷰 — Codex 지적, CRITICAL):** 위 문장은 "핀을 보는" 조회 경로에만 해당하고, **체크인 확인 핀(드래그로 위치를 조정·확인하는 단계)에는 적용되지 않음** — 이건 별개의 문제로, 지금까지 4라운드 리뷰 내내 방치돼 있었음. 확인 핀 화면의 기본 경로("그대로 확인" 버튼)는 이미 일반 버튼이라 VoiceOver로 문제없이 접근 가능하지만, **핀 위치가 틀렸을 때 드래그로 고치는 보정 경로는 VoiceOver 사용자에게 대체 수단이 없음** — 순수 드래그 제스처라 스크린리더로 조작 불가. 1단계는 창업자 본인(비 VoiceOver 사용자)이 유일한 타겟이라 지금 당장 이 gap이 실사용을 막지는 않지만, 문서가 "추가 설계 불필요"라고 잘못 주장하고 있었던 걸 정정. 실제 인터랙션 설계(예: VoiceOver 조정 액션으로 상/하/좌/우 미세 이동, 또는 좌표 직접 입력 대체 경로)는 진지한 설계 고민이 필요한 작업이라 TODOS.md로 유예(T31 아님 — 문서 정정 자체는 이 리뷰에서 즉시 반영, 실제 UI 설계는 별도 유예).

**첫 실행 온보딩 + empty state (확정, 2026-08-22 — 마지막 남은 항목 해소):** 별도의 "환영합니다" 슬라이드 없이 **알림 priming 화면이 곧 첫 화면이자 온보딩 전부**(미니멀 원칙 — 앱이 하는 일이 한 줄로 설명 가능할 만큼 단순함). priming 화면에서 알림 빈도(매시간/3시간마다/끔) 선택 + "허용하기" → OS 알림 권한 팝업 → 결과에 따라 위 배너 로직 적용, 오늘 뷰로 진입. **위치 권한은 온보딩에 포함하지 않음** — 대신 사용자가 처음 "체크인" 버튼을 누르는 순간 맥락 있게(contextual) OS 위치 권한 팝업이 뜬다. 근거: 권한 두 개를 한꺼번에 요청하면 거부율이 올라가고, 방금 누른 액션과 바로 이어지는 팝업이 맥락이 명확해 승인율이 높다는 게 일반적인 iOS 권장 패턴. 첫 오늘 뷰 empty state: 위치 권한이 아직 없어 지도에 내 위치 파란 점이 없음(2026-08-23 수정 — 이전엔 이 안내 텍스트를 지도 중앙에 겹쳐 띄우기로 했으나, 지도는 배경이 항상 바뀌는 표면이라 그 위의 옅은 텍스트는 명도 대비 4.5:1 기준을 보장할 수 없음/Codex·Claude 서브에이전트 둘 다 지적 — 대신 지도는 비워둔 채로, 안내 텍스트는 아래 바텀시트 쪽으로 통합); 바텀시트는 (2026-08-22 수정: 리스트가 지나간 시간대만 표시하는 규칙으로 바뀌면서) 첫 알림이 아직 안 왔으면 빈 리스트에 옅은 안내 텍스트 한 줄("아직 기록이 없어요 · 체크인하면 지도가 채워져요")만 표시 — 바텀시트 표면(고정 배경색, 대비 보장됨) 위에만 배치, 점선 원 여러 개를 미리 늘어놓지 않음.

## Brainstorming Review Log (2026-08-21)

/superpowers:brainstorming로 이 설계 문서에 대해 새로운 시각에서 구멍을 찾는 세션을 진행. 이미 eng-review/design-review를 거친 문서라 그 두 리뷰가 놓친 지점 위주로 6개 항목을 검토, 전부 결정 완료:

1. **데이터 유실 리스크 비대칭** — SQLite 쓰기 실패는 critical gap으로 다뤘으나 기기 분실/앱 삭제 시 전체 기록 영구 소실은 스코프 밖이었음. → 1단계는 리스크 감수, 2단계 클라우드 동기화로 해결 (Failure modes 표, 결정된 사항 반영).
2. **알림 문구의 톤 미적용** — 화면 UI는 전제#6을 반영했지만 알림 배너 문구는 스펙에 없었음. → 고정 문구 하나로 확정 (Visual Design Decisions 반영).
3. **"이전 체크인과 같은 장소" 버튼의 데이터 왜곡** — 실내에 오래 머물면 실제 이동이 감춰짐. → 드래그 가능한 지도 핀으로 대체 (GPS/실내 정확도, T5, Check-in Flow Diagram 반영).
4. **완료율 성공기준의 novelty effect / 표본 크기 문제** — 목표가 빠른 개발/서비스화로 조정되며 논의 방향이 바뀜. → 정량적 % 게이트 제거, 정성적 판단으로 대체 (Success Criteria, 전제#2 반영).
5-6. **알림 재스케줄링 트리거 취약점 + 재스케줄링 API 실패 미커버** — 유사 컨셉 실사용 앱 SetLog(설로그) 조사 결과, 방해금지 시간을 앱이 직접 설계하지 않고 OS Focus/DND에 위임 + 빈도 설정(매시간/3시간마다/끔, 사용자 직접 확인)만 제공하는 패턴 확인. → 커스텀 방해금지 시간대 계산 제거, SetLog 패턴 채택 (알림 스케줄링, T2, UNRESOLVED DECISIONS 반영). 재스케줄링 API 실패는 낮은 우선순위 gap으로 Failure modes 표에 추가만 하고 감수.
